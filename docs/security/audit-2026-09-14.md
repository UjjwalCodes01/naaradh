# Implementation audit — 14 Sep 2026

A read-through of the whole codebase against CLAUDE.md's invariants, done after Phase 3, with
the honest result: the architecture holds, the invariants are enforced where they should be,
and five real defects were found and fixed the same day. Nothing here was found by a test; all
five came from reading the code end to end. Each is now covered by a test or a boot-time check.

## Method

Traced one COD order webhook → intent → gate → dispatch → engine event → outcome → billing →
write-back → merchant webhook, then every failure branch; traced one inbound call → admission →
tools → cancellation → transfer; read every migration's RLS policy, grant and SECURITY DEFINER
function; read the auth paths (API keys, magic links, IAP), the erasure routine, the logger
redaction, the Terraform key-holder map and the CI gates. Cross-checked the phase reviews, the
go-live guide and `docs/security/checklist.md` against the code.

## Fixed

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | HIGH | **Production could run the simulator engine with the repository's development webhook secret.** `infra/envs/prod-in.tfvars` set `ENGINE_DEFAULT_IN = "simulator"` and nothing refused it; `SIMULATOR_WEBHOOK_SECRET` defaulted to a public constant, so anyone holding a tenant's engine tag could forge "signed" call events, and a real order would silently never be dialled. | `refineEngineEnv` in `packages/engines/registry` (applied by hooks, voice, workers): in production the simulator is refused unless `SIMULATOR_ALLOWED=true`, and the development secret is always refused. Stage sets the flag and holds a real secret (`SIMULATOR_WEBHOOK_SECRET`, optional secret in the key-holder map). Unit test `packages/engines/registry/test/env.test.ts`. |
| 2 | HIGH | **Merchant webhook URLs were an SSRF.** `POST /v1/webhooks` accepted any `https://` URL; the deliveries worker POSTed signed payloads to it from inside the VPC — an IP literal, `*.run.app` (our own internal services), or a public name later re-pointed at a private address. | `webhookUrlProblem` (`packages/shared/src/webhook-url.ts`: https only, no credentials, port 443, no IP literals, no local/internal/our-own hostnames) at registration, and `assertPublicDestination` in the deliveries worker resolves the name just before connecting and marks the delivery `dead` when any address is private (loopback, link-local incl. the metadata server, RFC 1918, CGNAT, ULA, multicast). 38 unit tests. |
| 3 | HIGH | **`trustProxy: true` in api, hooks, voice and console.** Fastify then takes the client IP from the first `X-Forwarded-For` entry, which the client controls: API-key IP allow-lists (E-70) and per-IP rate limits (public site keys, hooks, voice) were bypassable with one header. | `TRUST_PROXY_HOPS` in the shared base env (default 0 = no proxy) → `trustProxyOf()`; Terraform sets `2` (Cloud Run front end + external LB) for public services. `[VERIFY]` the hop count on stage against `httpRequest.remoteIp`. |
| 4 | MEDIUM | **Erasure left the caller's words behind.** `agent_actions.args` keeps tool arguments — `request_address_change.new_address_summary` and `create_ticket.summary` are free text a person spoke — and `scrubArgs` only drops PII-shaped keys, so an erased subject's address survived in `agent_actions`. | `eraseSubject` now replaces `args` and `result` with `{erased: true}` for every action of the subject's attempts; asserted in the erasure integration test. |
| 5 | LOW | **The OpenAPI description invented a rate limit** ("60 requests/minute nominal, 120 burst"); the limiter is a flat 120 per minute. Two checklist rows cited test files by names that do not exist. | Wording corrected; evidence paths fixed to the real files. |

## Confirmed sound (read, not assumed)

- Every outbound dial goes through `gateIntent()` inside the tenant transaction, and the attempt
  row is committed before `placeCall` (no phantom calls). Windows are luxon in the recipient's
  zone with the 5-minute close buffer; transactional intents past `not_after` are refused with
  `window:transactional_expired`, never re-queued.
- Consent is required for promotional and service purposes from the ledger only; `import` and
  `attestation` sources are never sufficient; suppressions are checked before consent and a
  global one wins.
- Billing: `isBillable` is the single verdict (superseded → not human → outcome set → minimum
  human speech); metering is keyed by outcome id under a per-tenant advisory lock; a duplicate
  `call.ended` is a no-op because the outcome row already exists.
- Engine events: deduped in hooks on `eventId`, out-of-order events ignored on terminal
  attempts, unsigned vendors re-fetched before an outcome is written.
- Inbound: the tenant comes only from `resolve_inbound_number()`; tools find the attempt by the
  vendor call id under RLS (a payload cannot point a tool at another tenant's call); the
  cancellation is two-step with a hashed single-use token; transfers use only the profile's
  verified target; addresses become tickets.
- RLS is forced on every tenant table; the app role has no INSERT on `numbers`, no grants on
  `login_tokens`/`shopify_sessions`; every SECURITY DEFINER function validates its inputs and the
  Shopify-install one is advisory-locked per shop.
- Magic links: 32 random bytes, SHA-256 at rest, 15 minutes, spent by one `UPDATE … WHERE
  used_at IS NULL`; sessions `__Host-` in production, 7-day absolute and 12-hour idle lifetimes
  enforced in SQL; IAP JWTs verified for alg, kid, signature, iss, aud, exp, iat.
- Idempotency keys are per tenant with request-hash comparison; the public site key can only
  create `lead_callback` intents and only from an allow-listed Origin.

## Not fixed (known, deliberate)

- When an engine cannot report the disclosure (`capabilities().reportsDisclosure = false`), the
  answer time is recorded as the disclosure time because the first utterance *is* the
  disclosure. This is a design decision (ADR-0006), not a measurement; the bake-off must check
  that the chosen engine can report it.
- `handleDispatchError` retries an unknown engine error every 5 minutes until `not_after`. For a
  promotional intent that can be days of failed attempts; acceptable until real engine error
  classes are known.
- Billing periods are UTC months (`billing_ledger.period`), not IST months. Documented in the
  billing runbook; change with an ADR if merchants object.

## Still open after this audit

The same items as the Phase 3 review: nothing has been applied to Google Cloud, the load
thresholds are unmeasured, the legal pages are drafts, and the engine adapter waits on
ADR-0001. The audit of the two long-lived apps (`apps/web`, `apps/shopify`) was lighter than
the services: their server actions all go through `requireSession(role)` and `withTenant`,
but a page-by-page review before launch is still due.
